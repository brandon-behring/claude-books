_The spine's second axis was coordination, and its reframing was sharp: a new unit of work gets a separate window. This chapter develops the primitive that embodies that — the sub-agent. Its defining architectural value is **conversation-history isolation**. A configuration may also select a different model, effort level, tools, memory, or MCP servers, but those are explicit specialization choices rather than consequences of spawning another window. Keep the two ideas separate: reach for a sub-agent when isolation, parallelism, or a focused role earns its cost; choose its capabilities deliberately._

## Isolation is the primitive; capability is configured

Start from what a sub-agent *is*, because two different ideas are often collapsed. Anthropic describes each sub-agent as running in its own context window, with a custom system prompt, specific tool access, and independent permissions.<Tag kind="official" /><Citation src="anthropic-subagents-docs" /> When a side task would otherwise flood the main conversation, the sub-agent performs that work in its own context and returns a summary.<Tag kind="official" /><Citation src="anthropic-subagents-docs" /> The **conversation history** is isolated; the environment is not necessarily isolated. By default the worker starts in the same working directory and can share project files and inherited tools, while `isolation: worktree` creates a separate repository worktree.<Tag kind="official" /><Citation src="anthropic-subagents-docs" />

So the invariant value is the *window*. By default a sub-agent inherits the main conversation's model, but its definition or invocation may select another allowed model and override effort; it can also narrow tools or add sub-agent-scoped MCP access.<Tag kind="official" /><Citation src="anthropic-subagents-docs" /> Spawning alone does not make reasoning stronger. Any capability change comes from those explicit controls, while isolation comes from the separate history.

<KeyIdea>
A sub-agent is first a **conversation-history isolation primitive**. It can also be specialized with a different model, effort, prompt, tools, memory, or MCP servers, but those are configured capabilities. Ask two questions separately: *does this work deserve its own trajectory?* and *what capability should that trajectory receive?*
</KeyIdea>

<MarginNote variant="note" label="Note">
"Isolation is the primitive; capability is configured" is this book's framing. The primary documentation establishes both halves: fresh conversation history, and explicit controls for model, effort, prompt, tools, skills, memory, permissions, worktree isolation, and MCP servers. Do not turn the framing into the false claim that every sub-agent uses the same model or tool surface.
</MarginNote>

## The contract: fresh history, configured context, bounded communication

Isolation is only *composable* if the boundary is well-defined in both directions, and it is. A named sub-agent starts with **fresh conversation history**: it does not receive the parent's conversation or tool results, nor the parent's full system prompt.<Tag kind="official" /><Citation src="claude-agent-sdk-subagents" /> But "fresh" does **not** mean empty. Claude Code composes startup context from the agent's own system prompt, the delegation message, tool definitions, permission context, most CLAUDE.md and memory layers, a conditional git-status snapshot, and any explicitly preloaded skills; Explore and Plan intentionally omit CLAUDE.md and git status. A conditional sibling roster also appears when `SendMessage` is available and another named agent exists.<Tag kind="official" /><Citation src="anthropic-subagents-docs" />

On normal completion, the Agent result carries the sub-agent's final response while intermediate reads and tool calls remain in its separate transcript; the parent may summarize that result.<Tag kind="official" /><Citation src="claude-agent-sdk-subagents" /> That is the usual return path, not the only possible communication. Suitably equipped named agents can receive mid-task direction through `SendMessage`, be resumed later under the same agent ID, and communicate with named peers; those messages cross the boundary without merging the transcripts.<Tag kind="official" /><Citation src="anthropic-subagents-docs" />

<ConceptBox term="The fresh-history / configured-context / bounded-communication contract">
A named sub-agent starts without the parent's conversation history, then Claude Code composes startup context from its definition and environment. Its completion result normally crosses back through the Agent tool; optional direction, resumption, and peer messages can also cross when enabled. The verbose middle — reads, tool calls, and dead ends — stays in the separate transcript. Isolation is therefore a controlled history boundary, not a claim that the worker literally inherits nothing or shares no state.
</ConceptBox>

There is one deliberate exception, and naming it sharpens the rule. A **fork** inherits the entire conversation so far, including the same system prompt, tools, model, and message history. Start one explicitly with `/fork`, or let Claude request the `fork` agent type where that capability is enabled.<Tag kind="official" /><Citation src="anthropic-subagents-docs" /> The return boundary stays narrow: the fork's tool calls remain outside the main transcript and only its result comes back. Named subagents are therefore the fresh-history default; a fork is the deliberate choice when reconstructing the parent's context would cost more than carrying it forward.

<MarginNote variant="note" label="Note">
Fork spawning by the model remains an evolving Claude Code capability. Treat `/fork` and the documented `fork` agent type as the current interface, and re-check the live subagent documentation before building durable orchestration around it.<Citation src="anthropic-subagents-docs" />
</MarginNote>

## Isolation buys separation of concerns

Why is a separate window worth the trouble? Because it separates **reasoning trajectories**. Anthropic's multi-agent write-up names the payoff directly: a sub-agent "provides separation of concerns—distinct tools, prompts, and exploration trajectories—which reduces path dependency and enables thorough, independent investigations."<Tag kind="official" /><Citation src="anthropic-multi-agent-research" /> Sub-agents "facilitate compression by operating in parallel with their own context windows,"<Tag kind="official" /><Citation src="anthropic-multi-agent-research" /> each compressing its slice of the work rather than sharing one crowded window. This does not imply total non-interference: agents can still affect a shared checkout or external system unless tools, permissions, worktrees, and coordination rules prevent it.

The separate window is not just hygiene, then — it is the property that makes the next move (assigning roles) possible. Two investigations in one window share a single trajectory; two separate windows reduce path dependence. Independence still has to be earned with distinct evidence, tests, or configurations rather than inferred from the number of agents.

## Roles compose instructions, capability, and execution controls

If isolation gives you separate trajectories, a **role** is how you specialize one. The core is a description plus system prompt, combined with capability and execution controls: model, effort, allowed and denied tools, permissions, skills, memory, MCP servers, hooks, turn limits, and optional worktree isolation.<Tag kind="official" /><Citation src="anthropic-subagents-docs" /> Use only the controls the job needs. The design principle remains blunt: "each subagent should excel at one specific task."<Tag kind="official" /><Citation src="anthropic-subagents-docs" />

The most productive role decomposition the sources demonstrate is **generate-then-verify** — focused generators plus a *separate* reviewer. Claude Code's code review runs it concretely: "Each agent looks for a different class of issue,"<Tag kind="official" /><Citation src="claude-code-review-docs" /> and then "a verification step checks candidates against actual code behavior to filter out false positives."<Tag kind="official" /><Citation src="claude-code-review-docs" /> The product announcement says the same in plainer words — the agents "look for bugs in parallel"<Tag kind="official" /><Citation src="claude-code-review-blog" /> and then "verify bugs to filter out false positives."<Tag kind="official" /><Citation src="claude-code-review-blog" />

<InsightBox title="A separate verifier reduces trajectory anchoring">
A verifier in a fresh history does not see the generator's chain of attempts unless you pass it, so it is less anchored to that trajectory. It can still share the same model's systematic blind spots, training, project state, or bad assumptions. Make the review meaningfully independent with different evidence, executable checks, adversarial criteria, or—when justified—a different model or tool configuration. Separation helps; it does not certify correctness.
</InsightBox>

<MarginNote variant="note" label="Note">
The **Planner / Generator / Evaluator** naming is this book's framing for that decomposition — a vocabulary laid over the anchored one-task principle and the generate-then-verify split, not a term the primaries use for sub-agents.
</MarginNote>

## When a sub-agent earns its keep

Isolation is not free, and the honest rule is a tradeoff, not a default-on. The **benefit** side: delegating verbose work (running tests, fetching docs, processing logs) keeps that output in the sub-agent so "only the relevant summary returns to your main conversation,"<Tag kind="official" /><Citation src="anthropic-subagents-docs" /> and the multi-agent architecture "distributes work across agents with separate context windows to add more capacity for parallel reasoning."<Tag kind="official" /><Citation src="anthropic-multi-agent-research" /> The **cost** side, stated just as plainly: "Subagents start fresh and may need time to gather context"<Tag kind="official" /><Citation src="anthropic-subagents-docs" /> — a latency hit — and the task's value "must be high enough to pay for the increased performance."<Tag kind="official" /><Citation src="anthropic-multi-agent-research" />

<KeyIdea>
Reach for a sub-agent when there is **large or irrelevant context to quarantine**, a **parallelizable focused subtask**, or a **clean-room review** to run. Stay on the main thread when **latency dominates** (a fresh agent must re-gather context) or the **task value doesn't clear the cost**. Isolation is the lever; the question is always whether this task is worth a fresh window.
</KeyIdea>

The quantified side of that cost — how many more tokens, how much more latency — is the Operations volume's subject; this chapter asserts the tradeoff qualitatively and leaves the numbers to where they can be measured.

<WorkedExample id="ch18-quarantine-or-not" title="Two delegations: one earns the window, one doesn't">

An agent is mid-task and faces two side jobs. Which should be a sub-agent?

- **"Run the full test suite and tell me what failed."** Verbose output (thousands of lines), most of it irrelevant to the main thread. Delegate it: the sub-agent runs the suite in its own window and returns only the relevant summary,<Citation src="anthropic-subagents-docs" /> keeping the noise out of your context. The isolation pays.
- **"Rename this variable in the file you're already editing."** Tiny, and it needs the context you already hold. A fresh sub-agent would start cold and "need time to gather context"<Citation src="anthropic-subagents-docs" /> you already have — pure overhead. Stay on the main thread.

Same primitive, opposite verdicts — because the first question is not "can some sub-agent configuration do this?" but "is there a separate trajectory worth paying for here?"

</WorkedExample>

<Pitfall title="Reaching for a sub-agent to add intelligence">
The misuse is assuming that another window is automatically more intelligent. With the default inherited model and tools, the certain change is a fresh trajectory plus its startup cost. A deliberately stronger model, higher effort, specialized prompt, or unique MCP server can change capability—but say which control does that work, measure whether it helps, and price it. Do not credit the mere existence of a sub-agent.
</Pitfall>

## Patterns

**Quarantine verbose work.** *Sketch:* delegate high-volume, low-relevance work (tests, doc fetches, log scans) to a sub-agent; keep the completion result concise. *When to use:* any side task whose output would crowd the main window.<Citation src="anthropic-subagents-docs" /> *Mechanics:* pass a focused prompt; the sub-agent's verbose middle stays in its transcript, while the normal Agent result returns. *Remember:* the win is the quarantine, not an assumed intelligence increase.

**Fresh-trajectory verify.** *Sketch:* generate with one (or several) focused sub-agents, then review with a *separate* verifier. *When to use:* anything where seeing the generator's trajectory would anchor review.<Citation src="claude-code-review-docs" /> *Mechanics:* focused generators look for distinct issue classes; a verifier checks candidates against actual behavior to filter false positives. *Remember:* fresh history reduces path dependence, but shared model blind spots require independent evidence or executable checks.

**Scope the role, not just the prompt.** *Sketch:* define the role's instructions, model/effort, tools, permissions, memory, MCP access, and isolation deliberately. *When to use:* whenever a sub-agent should excel at one task and not wander.<Citation src="anthropic-subagents-docs" /> *Mechanics:* grant only what the task needs; one task per sub-agent. *Remember:* capability and execution scope are part of the role, not properties you infer from its name.

**Default to fresh history; fork on purpose.** *Sketch:* let named sub-agents start from their configured context; use a fork only when the task genuinely needs the parent's conversation. *When to use:* fork when reconstructing context would cost more than carrying it in.<Citation src="anthropic-subagents-docs" /> *Mechanics:* named agents receive a delegation plus configured startup context; a fork inherits the full parent conversation. *Remember:* a fork trades input isolation for continuity — reach for it deliberately, not by habit.

## Quick reference

- **What it is:** a separate conversation history with a configurable role — **isolation is intrinsic; capability is configured**.<Citation src="anthropic-subagents-docs" />
- **The contract:** fresh conversation history, explicitly composed startup context, a normal Agent-result path, and optional bounded messaging/resumption.<Citation src="anthropic-subagents-docs" /><Citation src="claude-agent-sdk-subagents" />
- **Fork:** the deliberate continuity option; it inherits the full parent conversation while keeping its intermediate tool work out of the main transcript.<Citation src="anthropic-subagents-docs" />
- **Why isolate:** separation of trajectories reduces path dependence; shared files, external effects, and systematic blind spots remain.<Citation src="anthropic-multi-agent-research" />
- **Roles:** instructions plus model/effort, tools, permissions, memory, MCP access, hooks, and optional worktree isolation; grant only what the task needs.<Citation src="anthropic-subagents-docs" />
- **When:** quarantine context / parallelize / run a fresh-trajectory review. **When not:** latency dominates, or task value doesn't clear the cost.<Citation src="anthropic-multi-agent-research" /> (Quantified cost → the Operations volume.)

A teammate says, "Let's add a sub-agent so the system can handle the hard math it keeps getting wrong." Name the mental-model error in one sentence, and state what a sub-agent actually adds. Under what *different* framing (if any) could a sub-agent legitimately help with the math task?
</Exercise>

<Practice id="ch18-pr-1" difficulty="3">
Take an agent you run. Identify one side task that *should* be a sub-agent and one that should *not*, and justify each by the contract — what context gets quarantined (or wastefully reconstructed), and what result would return. For the one that should be a sub-agent, decide whether it should use a named agent's fresh history or a fork of the current conversation, and say why. The point is to feel the decision turn on *context to isolate*, not on *capability needed*.
</Practice>

<ExerciseSolutions>

<Solution for="ch18-ex-1">
The error is assuming **spawning itself adds capability**. What it certainly adds is a fresh, separate history. Under the default inherited model and tools, the math ability may not change, so a useful isolation framing is to have a fresh verifier check the answer against executable computation or to quarantine verbose symbolic work. A different configured model, higher effort, or specialized tool can also improve the task, but then the capability comes from that explicit configuration—not from the mere fact that it is a sub-agent. A second trajectory may still share the first model's blind spots, so verify against evidence rather than counting agents.
</Solution>

<Solution for="ch18-pr-1">
A representative pass. **Should be a sub-agent:** "summarize the 2,000-line dependency-audit log." It quarantines a large, low-relevance output — the sub-agent reads the log in its own window and returns only the few findings that matter, so the main conversation never carries the 2,000 lines. It should use a **named sub-agent with fresh history**: the delegation can name the log, and carrying the full conversation would cost window for no benefit. **Should not be a sub-agent:** "fix the typo in the function we're editing." It needs context the main agent already holds, the output is trivial, and a fresh sub-agent would pay startup latency to reconstruct what's already in hand — pure overhead. The decision turned on *context to isolate* (lots, in the first; none, in the second), exactly as the contract predicts — never on whether a sub-agent *could* do it.
</Solution>
