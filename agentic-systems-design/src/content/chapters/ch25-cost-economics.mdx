_ch24 surfaced the numbers; this chapter asks what they mean. Cost is the third operational surface, but it does not have one universal dominant term. A long tool-using trajectory may repeatedly carry far more input than it emits. A generation- or thinking-heavy workload can pay more for output, whose per-token rate is higher in the current pricing table. Server-side tools and hosted runtimes can add charges beyond tokens. The discipline begins by measuring the bill's mix, then applying the levers that target its largest terms._

## The bill is workload-shaped

Start with the terms the provider actually prices. A request can include uncached input, cache creation, cache reads, and output, each at its applicable rate. Model selection and modifiers such as Batch or data residency change those rates; server-side tools can add usage charges of their own.<Tag kind="official" /><Citation src="anthropic-pricing" /> In Claude Code, extended-thinking tokens are billed as output tokens.<Tag kind="official" /><Citation src="claude-code-costs" /> The cost driver is therefore whatever terms are largest for **this workload**, not a category chosen in advance.

Context remains an important engineering variable. It is "a critical but finite resource for AI agents,"<Tag kind="official" /><Citation src="effective-context-engineering" /> and tool-using loops often resend system instructions, conversation history, and tool results. That repeated input can dominate a long trajectory, especially when cache reuse is poor. But the conclusion is conditional: an output-heavy report, a large thinking budget, paid searches, or hosted tool execution can move the bill elsewhere. Current official pricing explicitly counts both input and output tokens and any additional server-side-tool charges.<Citation src="anthropic-pricing" />

Model the bill as a sum, not a slogan: **uncached input × its rate + cache writes × their rate + cache reads × their rate + output × its rate + tool/runtime charges**, with model, provider, geography, speed, and batch modifiers applied where relevant. Then measure those quantities at the same scope as the bill — per request, run, workflow, or team. A token total without token classes and rates can hide the real driver.

<KeyIdea>
Do not assume the dominant term. Measure uncached input, cache creation, cache reads, output, and tool or runtime charges under the rates that actually apply. Repeated context is often the largest opportunity in long agent loops; output-heavy, thinking-heavy, or server-tool workloads can be different. Optimize the measured bill, not a universal token story.
</KeyIdea>

</MarginNote>

## Prompt-cache economics: a read-vs-write asymmetry

When repeated input is material, prompt caching is a powerful lever. It stores reusable prompt prefixes server-side, and its economics are a sharp **asymmetry** between writing the cache and reading it.

The current first-party multipliers are worth stating exactly: a 5-minute cache write costs **1.25×** base input, a 1-hour write costs **2×**, and a cache read costs **0.1×**.<Tag kind="official" /><Citation src="anthropic-prompt-caching" /><Citation src="anthropic-pricing" /> A hit refreshes the applicable TTL at no additional charge, so reuse within that window amortizes the write.

The break-even follows from those numbers: caching pays after one read for the 5-minute duration and after two reads for the 1-hour duration.<Tag kind="official" /><Citation src="anthropic-pricing" /> The structural move is to stabilize a genuinely reusable prefix — system instructions, tool definitions, or a fixed document set — and choose a TTL whose expected reuse justifies its write premium. If the prefix changes before reuse or requests arrive outside the TTL, caching may not be the winning term.

<InsightBox title="A high read-to-creation ratio means caching is working">
The cache turns a per-run health metric into a cost signal. Claude Code surfaces per-turn cache reads "billed at roughly 10% of the standard input rate"<Tag kind="official" /><Citation src="claude-code-prompt-caching" /> — the harness-side restatement of the 0.1× read multiplier. And the signal to watch is the ratio between them: "A high read-to-creation ratio means caching is working well."<Tag kind="official" /><Citation src="claude-code-prompt-caching" /> Lots of reads per write means the cache is amortizing. Persistently high creation calls for diagnosis: the prefix may be changing, entries may be expiring, or traffic may not reuse the prefix often enough.
</InsightBox>

<MarginNote variant="warning" label="Warning">
The cache ratios and break-even are current as of 2026-07-14 and stated as multiples, not dollars. They can change, so fetch the live pricing and cache documentation for a real budget.
</MarginNote>

The ~10× gap between standard input and a cache hit makes a large, stable prefix much cheaper to reuse. It is a conditional advantage: the prefix must match, the workload must reuse it, and reuse must happen within the selected TTL.

## The multi-agent token multiplier — a modeling input, not a verdict

The second thing the cost surface has to handle is the one the orchestration chapters deferred: multi-agent systems can be *expensive*, and the honest question is when that expense is worth paying. Anthropic's first-party measurement on its own research system is concrete: "agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats."<Tag kind="official" /><Citation src="anthropic-multi-agent-research" /> Each sub-agent runs its own context window, so topology can multiply token use; ~15× is a prior that tells you to measure, not a forecast to paste into your budget.

But the same measurement reframes the burn. On their benchmark, "token usage by itself explains 80% of the variance"<Tag kind="official" /><Citation src="anthropic-multi-agent-research" /> in performance. Read together, the findings show that extra spend can buy performance on a suitable task. The cost-modeling question is not "is multi-agent wasteful?" or "does every task clear 15×?" It is "**does this workload's measured quality gain justify this workload's measured multiplier?**"

<Pitfall title="Reading the 15× as a universal anti-pattern">
The ~15× is one first-party datapoint, measured on Anthropic's own multi-agent research system, and the "80% of the variance" is on the BrowseComp benchmark specifically — both are *measurements on one workload*, not constants you can carry to yours. Reading "15×" as a flat verdict misuses it in one direction; reading "80%" as "always spend more" misuses it in the other. Use the result as evidence that topology can create a large, sometimes valuable multiplier, then gather your own cost and quality measurements before choosing it.
</Pitfall>

This is also why this chapter, not the orchestration ones, is the honest home for the ~15×. Whether to *build* a multi-agent topology is an orchestration question; what it costs on your workload and whether the measured gain justifies it is an economics question.

## Changing rates: model tiers and the Batch API

After reducing expensive token or tool volume and improving reuse, two levers change the rates applied to work that remains.

The first is **model-tier routing**. Anthropic's guidance is to "Choose Haiku for simple tasks, Sonnet for most production workloads, and Opus for the most complex reasoning."<Tag kind="official" /><Citation src="anthropic-pricing" /> Treat that as a qualitative routing guide and use evals to choose the cheapest model that clears each subtask. A classification or extraction step may not need the same tier as complex reasoning; the point is to measure quality per subtask instead of assigning the most expensive model to the whole run by default.

<MarginNote variant="tip" label="Tip">
Render the tier ladder as a routing example, not a price list. The pricing page is volatile (verified 2026-07-14). If you need absolute prices, fetch them live; do not carry a remembered figure into a cost model. The lineup also evolves — treat the named tiers as a qualitative capability choice, not a complete or fixed roster.
</MarginNote>

The second is the **Batch API**, for work that is not time-sensitive. It "allows asynchronous processing of large volumes of requests with a 50% discount on both input and output tokens"<Tag kind="official" /><Citation src="anthropic-pricing" /> — corroborated on the feature's own documentation, which describes processing large volumes "while reducing costs by 50% and increasing throughput."<Tag kind="official" /><Citation src="anthropic-batch-processing" /> The trade is latency for price: you give up real-time response and get half off. An overnight evaluation run, a bulk re-classification, a backfill — none of these needs to answer in seconds, and all of them halve in cost by going through the batch path.

The two levers are orthogonal to caching and to each other: tier-routing changes *which model* performs a subtask, batching changes *when* eligible work runs, and caching discounts repeated input. They can stack where the current pricing rules allow it.<Citation src="anthropic-pricing" />

## The levers, composed

The chapter's payoff is that the four operational levers are not competing guesses. Each acts on a different part of the measured spend:

- **Reduce the measured expensive volume.** Trim unnecessary input and tool results, cap unneeded output or thinking, and avoid paid tool/runtime work that adds no value. Target the term the measurements identify.
- **Cache reusable input.** Discount a matching prefix when expected reuse clears the write premium and TTL; watch the read-to-creation ratio to confirm it is amortizing.
- **Route by model.** Send each subtask to the cheapest model that clears its eval target.
- **Batch deferrable work.** Push eligible non-urgent requests through the 50%-off asynchronous path.

They compose because they act on different variables — quantity and type of work, repeated input, model, and timing. Topology is an upstream design choice rather than a discount lever: compare its measured cost and quality before applying the four. The Batch API applies to work you can defer, not to a live interactive turn. Apply only the levers that fit and verify the resulting bill.

<WorkedExample id="ch25-modeling-an-agent-bill" title="Modeling an agent's bill before redesigning it">

A team says: *"Our research agent's bill tripled this month and we don't know why. Do we kill the multi-agent design?"*

Measure the bill's terms before touching the architecture:

- **Locate the increase.** Compare uncached input, cache creation and reads, output and thinking, model mix, tool/runtime charges, topology, and request volume with last month. Larger histories may have raised input; a reporting workload may have raised output; a new search tool may add per-use charges. The measurements choose the branch.
- **Cache reusable input.** If repeated input is material, check the read-to-creation ratio and TTL. Persistently high creation may indicate prefix churn; low reuse may mean caching was never the right assumption. Stabilize only the content that is genuinely reusable.
- **Model the topology against value.** Weigh the team's measured multi-agent multiplier, not the published ~15× as a universal constant. Cutting agents may cut quality; keeping them may be waste if the task does not benefit.
- **Route and batch to cheapen what's left.** If some sub-agents are doing routine extraction on the top model tier, route them down to Haiku/Sonnet. If any of the work is a non-urgent backfill, send it through the 50% Batch API.

Notice the architecture question came after measurement. The cost surface turned "do we kill multi-agent?" into a set of testable terms instead of replacing one guess with another.

</WorkedExample>

## Quick reference

- **The premise:** cost is workload-shaped — separate uncached input, cache writes, cache reads, output, tool/runtime charges, model, and pricing modifiers before naming a driver.<Citation src="anthropic-pricing" />
- **Cache asymmetry:** 5-minute writes cost 1.25× base input, 1-hour writes 2×, and reads 0.1×; break-even is one or two reads respectively, provided the prefix matches within the TTL.<Citation src="anthropic-prompt-caching" /><Citation src="anthropic-pricing" />
- **Cache health = cost signal:** a high read-to-creation ratio means caching is working; high creation can reflect prefix churn, TTL expiry, or too little reuse and needs diagnosis.<Citation src="claude-code-prompt-caching" />
- **Multi-agent burn:** Anthropic measured ~4× (single agent) and ~15× (multi-agent) the tokens of a chat, with "token usage by itself explains 80% of the variance" — a cost-modeling input on *their* workload, not a universal constant or a flat anti-pattern.<Citation src="anthropic-multi-agent-research" />
- **Rate levers:** route the cheapest model that clears each subtask (qualitative — fetch live prices) and push non-urgent work through the 50% Batch API.<Citation src="anthropic-pricing" /><Citation src="anthropic-batch-processing" />
- **The playbook:** measure → reduce the expensive volume → cache reusable input → model topology against value → route and batch where applicable.

<Solution for="ch25-ex-1">
The four moves are **reduce measured expensive volume**, **cache reusable input**, **route to the cheapest model that clears the subtask**, and **batch deferrable work**. Reduction changes quantities — input, output/thinking, paid tool calls, runtime, or avoidable requests. Caching changes the effective rate for a matching reused prefix, subject to its write premium and TTL. Routing changes the model rate and capability. Batching changes timing in exchange for a 50% input/output discount. They can compose because they act on different terms, but measurement must choose the priority: an input-heavy loop, an output-heavy generator, and a server-tool-heavy research job do not share a guaranteed dominant lever.
</Solution>

<Solution for="ch25-ex-2">
The bare ~15× says Anthropic's research system spent much more than a chat. The "token usage by itself explains 80% of the variance" result adds that, on BrowseComp, higher token use was strongly associated with better performance. Together they show that a large multiplier can buy value on a suitable workload; they do not supply your multiplier or guarantee your gain. Misuse is treating ~15× as either a universal ban or a universal budget, or treating 80% as an instruction to spend more everywhere. Both are **measurements on one workload**. Measure your topology's cost and quality against a simpler baseline.
</Solution>

<Solution for="ch25-pr-1">
A customer-support agent searches a knowledge base and drafts replies. Measure each request's uncached input, cache creation and reads, output/thinking, model, searches, and total volume. If repeated articles dominate, keep only cited snippets; if long drafts or thinking dominate, constrain them where quality permits; if paid searches dominate, improve retrieval and reuse. Cache the stable system/tool prefix only when the observed reuse falls inside the TTL, and confirm with the read-to-creation ratio. Route routine classification to a cheaper capable model, reserve stronger models for cases that need them, and batch overnight re-tagging. If the agent fans out, compare its own topology multiplier and quality gain rather than importing ~15× as a forecast.
</Solution>

<Solution for="ch25-pr-2">
A fixed input-to-output ratio would turn one workload's traffic shape into a universal law. Input and output have different rates; cache classes have different rates; thinking is billed as output; tools and runtimes can add non-token charges; and the mix changes with task and topology. For a real model, fetch the current provider prices and modifiers, record usage separately for uncached input, cache creation, cache reads, output, tools, and runtime at the same scope as the invoice, apply the live rates, and compare the estimate with the authoritative billing surface from ch24. Investigate any residual rather than forcing it into a remembered ratio.
</Solution>
