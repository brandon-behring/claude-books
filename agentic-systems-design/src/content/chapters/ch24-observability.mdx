_ch21 placed observability as the **see** surface: once an eval defines what "good" means, observability helps reconstruct what happened against it. This chapter takes that surface apart. Its thesis is deliberately plural: a run leaves records in the agent harness, the telemetry pipeline, the systems the agent touched, and the billing system. None is complete by itself. The discipline is to preserve each source, correlate them, and know which question each source can actually answer._

## Reconstruct a run from multiple records

Claude Code normally stores a local **session transcript** as JSONL, with entries for messages, tool use, and metadata.<Tag kind="official" /><Citation src="claude-code-sessions" /> That is valuable evidence of what the harness sent, received, and attempted. It is not a universal ledger: transcript writes can be disabled, the on-disk entry format is internal and can change, and the transcript does not by itself prove the state reached by a remote API, database, git host, or deployment system.<Citation src="claude-code-sessions" />

The other records are independent evidence, not mere views of that file. OpenTelemetry exporters emit runtime metrics, events, and optional traces as the run executes; content is redacted by default, so telemetry can have timing and identifiers without the full conversation.<Tag kind="official" /><Citation src="claude-code-monitoring" /> External systems record effects — a commit SHA, CI run, database audit event, ticket transition, or API request — and are authoritative for their own state. Billing and usage systems own the charged quantities for the authentication and provider path in use.<Citation src="claude-code-costs" /> Reconstructing a run means joining those records by stable identifiers and time, then stating where gaps remain.

<KeyIdea>
There is no single observability record for an agent that can act on other systems. Correlate four evidence sources: the **session transcript** for harness-visible messages and tool activity, **runtime telemetry** for timing and execution signals, **external-system records** for effects, and **billing/usage records** for spend. Each can be authoritative for its own slice; none is complete for the whole run.
</KeyIdea>

<ConceptBox term="The correlated evidence bundle">
A reconstruction assembled from records with different owners and failure modes: transcript entries, OTel events/spans, external-effect records, and provider billing or usage data. Preserve shared keys such as `session.id`, `request_id`, `tool_use_id`, workflow/run IDs, and commit SHAs wherever the interfaces expose them. Correlation produces the incident view; it does not turn any one source into universal ground truth.
</ConceptBox>

## Session transcripts: one partial record, two retention paths

The transcript still matters, but its capture and retention need precise language. There are two persistence paths with different owners, and neither makes the transcript a record of effects outside the harness.

The first is the **CLI local record** under `~/.claude/projects/`. These files are removed after 30 days by default, configurable with `cleanupPeriodDays`; writes can also be suppressed entirely.<Tag kind="official" /><Citation src="claude-code-sessions" /> The entry schema is an internal Claude Code format, so use `/export` or structured interfaces for durable consumers instead of treating raw JSONL as a stable public API.<Citation src="claude-code-sessions" />

The second is the **SDK mirror**. `SessionStore` forwards locally written transcript entries to S3, Redis, a database, or another adapter; external retention is the adapter's responsibility.<Tag kind="official" /><Citation src="claude-code-session-storage" /> The mirror is explicitly best-effort: after bounded retries, a failed batch is dropped while the query continues, and operators must monitor `mirror_error` if completeness matters.<Citation src="claude-code-session-storage" /> A durable incident program therefore owns retention, validates the adapter, and monitors gaps rather than assuming "mirrored" means complete.

<InsightBox title="Two persistence paths, two failure modes">
The local file is time-bounded and can be disabled; the external mirror is operator-retained but best-effort. Decide what completeness you require before an incident, monitor the mirror, and remember that both paths contain the same harness-side evidence — neither substitutes for the records of systems the agent changed.
</InsightBox>

## OpenTelemetry GenAI conventions as the substrate

When you emit runtime telemetry, the design question is *which vocabulary do you instrument to?* The answer is a **vendor-neutral convention**, not a vendor-specific schema. Telemetry is produced during execution; it need not be generated by replaying a transcript.

Claude Code exports three OpenTelemetry signals — "metrics as time series data via the standard metrics protocol, events via the logs/events protocol, and optionally distributed traces"<Tag kind="official" /><Citation src="claude-code-monitoring" /> — and in the trace tree, "each user prompt starts a"<Tag kind="official" /><Citation src="claude-code-monitoring" /> `claude_code.interaction` root span, with API calls, tool calls, and hook executions as its children. Crucially, the per-LLM-request span's attributes align to the "OpenTelemetry GenAI semantic convention."<Tag kind="official" /><Citation src="claude-code-monitoring" /> That alignment is the whole point: Claude Code's span tree is **one realization** of a standard the spec defines independently.

On the spec side, the OpenTelemetry GenAI semantic conventions define the shared vocabulary. The standard token-usage metric is `gen_ai.client.token.usage`,<Citation src="otel-genai-metrics" /> documented as the "Number of input and output tokens used,"<Citation src="otel-genai-metrics" /> and agent operations include `create_agent` and `invoke_agent`.<Citation src="otel-genai-agent-spans" /> Instrumenting to the convention makes the telemetry portable across compatible collectors and backends. It does not make the trace complete: Claude Code tracing is opt-in, content fields are redacted by default, and a subprocess or remote service needs its own instrumentation.<Citation src="claude-code-monitoring" />

Two caveats are load-bearing, and both move on a release cadence. First, the OpenTelemetry GenAI semantic conventions carry Status: **Development** — the span and metric names above (`gen_ai.client.token.usage`, `create_agent`, `invoke_agent`) may still change before the convention stabilizes, so treat them as current-as-of, not final. Second, of Claude Code's three signals, metrics and events are GA while distributed **traces are beta**;<Tag kind="official" /><Citation src="claude-code-monitoring" /> a team relying on the `claude_code.interaction` span tree should track the beta-to-GA transition. Both warrant a recheck after **2026-08-25**.

<MarginNote variant="warning" label="Caveat">
The OTel GenAI conventions are Status: Development and the names here are feature-surface — re-verify `gen_ai.client.token.usage`, `create_agent`, and `invoke_agent` against the spec after 2026-08-25; they may drift before stabilization.
</MarginNote>

## Attribution is a correlation signal, not the approval gate

Attribution connects an external effect to the actor or workflow that produced it. In Claude Code, git attribution is configurable; commits carry a `Co-Authored-By` trailer by default, and that trailer can be customized or disabled.<Tag kind="official" /><Citation src="anthropic-settings" /> In CI, GitHub App identity provides another provenance signal.<Tag kind="official" /><Citation src="claude-code-github-actions" /> Neither signal alone identifies an exact session or trace. A reliable chain stores explicit correlation metadata — for example a session, trace, workflow, request, or tool-use ID — alongside the external record, then verifies the effect in the system that owns it. Claude Code telemetry exposes identifiers such as `session.id`, `request_id`, and `tool_use_id` for those joins.<Citation src="claude-code-monitoring" />

Here is the boundary the chapter will not let blur: attribution is a **provenance signal**, not an **approval gate**. It helps answer "where did this come from?"; it does not decide "may this proceed?". That decision — the human-in-the-loop review before an irreversible action — is the oversight workflow, and ch26 owns it. Read a trailer as either an exact run pointer or a gate and you have asked a label to carry evidence it does not contain.

<MarginNote variant="note" label="Note">
Provenance and approval both attach to the same PR, which is why they get confused. Attribution here is evidence about origin; exact run correlation requires an explicit shared identifier, and the gate (ch26) answers whether the change may proceed. A trailer is a label, not a checkpoint or a session ID.
</MarginNote>

## Billing and usage records — surfacing is not modeling

The fourth evidence source is the cost and usage a team actually watches. The in-CLI `/usage` command shows session token statistics, while organizational reporting depends on how Claude Code is authenticated: Teams and Enterprise use their organization analytics, API organizations use the Claude Console, and cloud-provider deployments use that provider's billing console.<Tag kind="official" /><Citation src="claude-code-costs" /> OpenTelemetry can stream near-real-time per-user usage into an observability stack, but it is another measurement path rather than a replacement for the applicable billing system.<Citation src="claude-code-costs" />

<MarginNote variant="tip" label="Tip">
The in-CLI usage command was renamed from `/cost` to `/usage`. Command names are feature-surface and drift per release — re-verify after 2026-08-25.
</MarginNote>

The local dollar figure carries a caveat that defines the boundary: it is "an estimate computed locally from token counts and may differ from your actual bill."<Tag kind="official" /><Citation src="claude-code-costs" /> For an API user, the Console is authoritative; for subscription and cloud-provider paths, the relevant organization or provider surface differs.<Citation src="claude-code-costs" /> Surfacing *shows* measurements and points to the applicable billing record; it does **not model the economics**. Which token class, model, cache behavior, tool charge, or runtime term drives the bill is ch25's workload-specific question.

<WorkedExample id="ch24-routing-an-observability-question" title="Routing an observability question to its surface">

A team says: *"We shipped a bad PR last week. We can't reconstruct the conversation and tool sequence, the trace backend doesn't recognize our spans, and the bill looks high — what failed and where?"*

Route each part to its surface before fixing anything:

- **"Can't reconstruct the conversation"** is a **transcript-retention** question. Check whether persistence was enabled, whether the local file survived the 30-day default, and whether the best-effort `SessionStore` mirror reported gaps. Even a complete transcript shows harness-visible activity, not the final state of every external system.
- **"Trace backend doesn't recognize our spans"** is a **tracing-convention** question. If its queries and dashboards expect vendor-specific names, portable OTel data will not have shared semantics. Instrument to the GenAI convention (`gen_ai.*`, `create_agent`/`invoke_agent`) so compatible tooling agrees on the fields — while remembering those names are still Development-status.
- **"We shipped a bad PR"** needs the **external git/CI record** plus correlation. A trailer or app actor is provenance, but an exact run link requires a stored session, workflow, trace, request, or tool-use identifier. Whether a human gate *should have stopped it* is ch26's oversight workflow.
- **"The bill looks high"** is a **billing/usage** question up to the number. Compare `/usage`'s local estimate with the authoritative surface for the authentication path. *Why* it is high and *how to reduce it* is ch25's modeling.

Four evidence sources turned one panicked failure into a reconstruction plan — and pulled the two decisions that *aren't* observability (the approval gate and the cost model) out to their real owners.

</WorkedExample>

<Pitfall title="Promoting one partial record to universal truth">
The recurring failure is asking one source to answer every question: using a transcript to prove a remote side effect, a trace to recover redacted content, a commit trailer to identify an exact session, or a local estimate as the bill. Build an evidence matrix before the incident: which source owns intent, execution timing, external state, and spend; which identifiers join them; and how each source can be absent or incomplete.
</Pitfall>

## Quick reference

- **Four partial sources:** session transcript, runtime telemetry, external-system records, and billing/usage data; correlate them rather than naming one universal ground truth.
- **Two transcript paths:** local files have a 30-day default and can be disabled; the SDK `SessionStore` mirror is externally retained but best-effort, so monitor `mirror_error`.<Citation src="claude-code-sessions" /><Citation src="claude-code-session-storage" />
- **Trace to the convention:** instrument to the OTel GenAI names (`gen_ai.client.token.usage`, `create_agent`, `invoke_agent`), not a vendor schema; Claude Code's `claude_code.interaction` tree is one realization.<Citation src="otel-genai-metrics" /><Citation src="otel-genai-agent-spans" />
- **Moving target:** the GenAI conventions are Status: Development and Claude Code's traces signal is beta — recheck names after 2026-08-25.<Citation src="claude-code-monitoring" />
- **Attribution = signal, not exact linkage or approval:** a trailer or app actor indicates provenance; store an explicit correlation ID to identify the run, and leave the gate to ch26.<Citation src="anthropic-settings" /><Citation src="claude-code-monitoring" />
- **Surfacing ≠ modeling:** `/usage` is a local estimate; compare it with the authoritative billing surface for the authentication path, then use ch25 to model the drivers.<Citation src="claude-code-costs" />

<Solution for="ch24-ex-1">
The four sources are: **session transcript** for the messages and tool activity visible to the harness; **runtime telemetry** for timing, errors, token counts, and execution relationships; **external-system records** for the state actually reached in git, CI, an API, or a database; and **billing/usage records** for charged usage under the active provider and authentication path. Each answers its own question and can be incomplete independently. A `Co-Authored-By` trailer or GitHub App actor is a **provenance signal**, not an exact run pointer; exact linkage needs a shared session, trace, workflow, request, tool-use, or equivalent identifier recorded on both sides. None of those signals approves the change. Approval is the ch26 human-in-the-loop gate.
</Solution>

<Solution for="ch24-pr-1">
A documentation-writing agent opens a bad PR. **Transcript:** local JSONL exists, but the team must either archive it before the 30-day sweep or monitor a `SessionStore` mirror for dropped batches. **Telemetry:** OTel records the session, request, and tool-use identifiers, timing, and errors; prompt and tool content remain redacted unless deliberately enabled. **External effects:** the git host and CI system hold the commit SHA, actor, checks, and merge event. The workflow writes its session or trace ID into a run record keyed by that SHA, so the records can actually be joined. **Billing:** `/usage` supplies a local estimate, while the organization's authentication path determines the authoritative reporting surface. During an incident, the most damaging gap is the missing cross-system identifier: all four records could exist yet remain impossible to join confidently. Adding a merge approval is still ch26; deciding which cost term to reduce is ch25.
</Solution>
